# Совместная разработка

## Начало работы

1. Клонируйте репозиторий и выполните быстрый запуск из README.
2. Создайте ветку `feature/<name>` или `fix/<name>` от `main`.
3. Вносите изменения небольшими завершёнными шагами; открывайте pull request в `main`.
4. В PR опишите поведение, способ проверки и ограничения. Дождитесь зелёных проверок CI.

Прямой push в `main` лучше ограничить настройками GitHub после публикации репозитория.
Адрес репозитория и права команды устанавливает владелец проекта.

## Границы модулей

- Роуты API не должны самостоятельно открывать FITS или знать детали IRSA.
- Адаптеры возвращают модели наблюдений и FITS; ошибки архива не превращаются в demo.
- Научные функции не зависят от HTTP, `.env` и очереди.
- Долгие вычисления запускаются через worker, а не внутри HTTP-запроса.
- Секреты, `.env`, настоящие FITS и временные результаты в Git не добавляются.

## Контракт фронтенда

Изменили публичную модель или маршрут — обновите OpenAPI:

```text
uv run python scripts/export_openapi.py
```

Добавьте обновлённый `docs/openapi.json` в тот же PR и согласуйте изменение с фронтендом.
В `packages/api-client` лежит тонкий клиент; схемы типов генерируются из OpenAPI.
Не удаляйте поля `/api/v1` без согласования. Серьёзные несовместимые изменения — новый `/api/v2`.

## Проверка перед PR

```text
uv run ruff check .
uv run ruff format --check .
uv run pytest -q
uv run python scripts/smoke.py
```

Тестируйте научные инварианты: знак разности, перенос дисперсий, геометрию WCS,
маски и отсутствие смешения провайдеров. Проверка настоящего архива запускается вручную:
нестабильность внешнего сервиса не должна ломать каждый PR.

## Зависимости и данные

Добавляйте зависимости через `uv add`, обновляйте `uv.lock` вместе с `pyproject.toml`.
При изменении SQLite нужна явная миграция с повышением `PRAGMA user_version`.
Новый релиз SPHEREx сначала проверяется live-тестом, затем меняются настройки коллекций;
не объединяйте дублирующие переработанные релизы одного наблюдения без правил дедупликации.
